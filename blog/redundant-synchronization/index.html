Reasoning About Redundant Synchronization

Ziwei Zhou · Research draft · October 18, 2026

Synchronization constrains the executions of a concurrent program. Reducing synchronization asks which constraints can be weakened while preserving the program’s required behavior. The answer depends on the input domain, the execution model, and the correctness contract.

These notes first define the program, input domain, and execution contract, then follow a finite double-buffer example. The example makes issue, completion, consumption, and reuse visible.

1. Formulating the problem

1.1 Programs, executions, and correctness

A program and its inputs

Let \(P\) be a GPU program containing computations, memory accesses, asynchronous operations, and synchronization. Its source may be handwritten CUDA or generated by a compiler such as Triton or TileLang. The definition concerns the resulting program at a chosen analysis level. In our SentryWard work, that level is primarily PTX; the compiler or library name does not determine the problem’s scope.

An input \(x\) fixes the relevant data, problem dimensions, and launch configuration. If data values remain symbolic, one configuration can denote a family of inputs. The target domain \(X\) specifies the inputs covered by a correctness claim. A proof for one fixed shape does not automatically cover a larger shape.

A contract over executions

An execution \(\tau\) records the actions that occur and their order: thread steps, asynchronous memory effects, and completion events. The execution model \(A\) determines which executions are allowed, including memory semantics and synchronization rules. The same program and input can admit several executions.

The correctness contract \(Q_x(\tau)\) states whether an execution meets the requirements for input \(x\). Requirements can include legal memory accesses, valid synchronization and resource lifetimes, required progress, and the intended numerical result under a declared arithmetic model. They are fixed before comparing program variants.

Write \(\operatorname{Exec}^{\max}_A(P,x)\) for the maximal allowed executions. A maximal execution finishes normally, stops with an error or deadlock, or continues indefinitely. A program meets the target contract when its execution set is nonempty on every input and every maximal execution satisfies \(Q\):

\[ \begin{aligned} \operatorname{Valid}_{A,X,Q}(P)\iff \forall x\in X:\quad &\operatorname{Exec}^{\max}_A(P,x)\ne\varnothing\\ &{}\land\ \forall\tau\in\operatorname{Exec}^{\max}_A(P,x),\ Q_x(\tau). \end{aligned} \]

The quantifiers cover every target input and every allowed execution on that input. Errors and deadlocks remain in the execution set; the contract evaluates nontermination under the chosen fairness and progress requirements. A finite prefix exposes intermediate behavior but need not be a completed execution. Finding one successful run cannot establish the universal claim.

A double-buffer illustration

For a running illustration, consider a producer and a consumer sharing two slots. Tile \(t\) uses slot \(t\bmod 2\). The producer issues asynchronous copies; the consumer issues computations that read the slots. A data-ready wait protects consumption, and a slot-reuse wait protects the previous tile from an overwrite.

With \(T=2\), neither slot is reused. With \(T=3\), tile 2 writes slot 0 again, so the consumption of tile 0 becomes relevant to the next write. The loop body is unchanged; the input changes which dynamic interactions occur.

One program, several executions

An asynchronous instruction’s issue is distinct from its later effects: a copy may have been issued while its destination is still unwritten, and a computation may have been issued before its memory reads or completion.

For tile \(t\), the illustration uses five events. \(I_t\) issues the copy, \(W_t\) writes the shared slot, \(J_t\) issues the computation, \(R_t\) reads the slot, and \(F_t\) finishes the computation. Write \(a\prec b\) for a required precedence: an execution satisfies it when \(a\) occurs before \(b\). The asynchronous dependencies include \(I_t\prec W_t\) and \(J_t\prec R_t\prec F_t\). The ready wait adds \(W_t\prec J_t\).

For the illustration only, \(A\) is a finite order model: every topological execution of the stated dependencies is allowed. Each tile has one atomic shared write and one atomic shared read, writes are immediately visible, and the illustration has no barrier counters or hidden scheduling priorities. A whole-slot ownership contract requires

\[ W_t\prec R_t, \qquad R_t\prec W_{t+2}\quad(t+2<T). \]

The first relation protects readiness; the second protects reuse. They form a sufficient discipline for the example’s intended slot generations. Real accesses can have finer footprints, and a whole-slot discipline can be stronger than necessary. Real PTX ordering also needs its own semantic justification.

Across iterations, producer order gives \(I_t\prec I_{t+1}\), and the retained consumer wait gives \(F_t\prec J_{t+1}\). The reuse wait adds \(F_t\prec I_{t+2}\) whenever the slot is reused. Together with the per-tile dependencies, these are all the model’s edges. In particular, the path \(R_t\prec F_t\prec I_{t+2}\prec W_{t+2}\) enforces the reuse duty.

The execution selector changes scheduling choices while leaving the selected program and input fixed. In the intact example, both displayed executions satisfy the stated ordering duties. After a wait is removed, a successful displayed execution need not rule out another execution that violates a duty. In this finite acyclic model, an ordering duty holds in every topological execution exactly when a directed path connects its two events. The figure uses that reachability check; the repository tests independently enumerate every reachable completed-event set. The illustration checks the stated ordering discipline, not the full kernel contract described above.

Candidate programs and input scope

The allowed edit family determines which candidates are considered. Deletion-only search fixes a set \(S\) of static synchronization sites and an editing rule \(\mathcal E\). A deletion set \(D\subseteq S\) produces \(P_D=\mathcal E(P,D)\), with \(P_{\varnothing}=P\). Deleting a static loop site changes every participating dynamic occurrence, not just the occurrence displayed in a figure. Only edits whose resulting program has defined semantics are admitted; protocol errors and deadlocks remain correctness failures.

If the target domain contains both inputs, a candidate must satisfy the contract at both. Correctness at the smaller input supplies no proof for the additional reuse interaction. This is an input-scope issue, independent of whether the kernel originated in CUDA or a compiler.

Deletion can change the candidate’s execution semantics, not merely remove an edge from an old drawing. The illustration deliberately uses pure ordering waits. Real synchronization can also change barrier counts, transaction expectations, phases, or visibility. Those effects must be reconstructed for the edited program before applying a local argument.

The general synchronization-reduction problem is therefore to find an allowed candidate \(P'\) satisfying \(\operatorname{Valid}_{A,X,Q}(P')\), while improving a stated objective. Fewer retained sites, lower kernel runtime, and lower search cost are distinct objectives. The formulation does not assume monotonicity under deletion or require preserving every internal order of the original program.
